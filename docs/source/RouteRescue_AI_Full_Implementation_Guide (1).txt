ROUTERESCUE AI
Full Implementation Guide
DEVHOST 2026 • PS 4.1: AI Agent for Travel Disruption Recovery
Prepared as a build-ready technical plan and presentation companion.
1. Executive summary
RouteRescue AI is a human-supervised agent that helps travellers recover from cancelled flights, major delays, missed connections, severe weather, or a disrupted transport leg. It assembles the current trip context, checks alternatives across supported travel modes, validates transfers and constraints, ranks feasible plans, and presents a clear explanation with source freshness and uncertainty. It does not autonomously spend money or change a booking.
Recommended design: LangChain Deep Agents for planning and delegation; a custom MCP server as the standard tool interface; REST API adapters for actual data providers; a deterministic feasibility/scoring service; FastAPI backend; React frontend; PostgreSQL or SQLite storage; and a labelled simulator for reliable demos. Deep Agents supports planning, subagents, skills, filesystem/context management, and MCP tools according to its official documentation [1]. MCP standardises how a client discovers and calls tools/resources/prompts; it does not itself provide travel data or guarantee an integration is correct [2].
2. Problem statement and scope
Source problem: PS 4.1, “AI Agent for Travel Disruption Recovery.” The expected prototype detects or simulates disruptions, identifies affected bookings, searches alternatives based on budget/timing/destination, and produces a recovery itinerary with proposed changes/actions.
MVP scope
Input: user-entered disruption or demo-triggered cancellation/delay; existing itinerary; origin/destination; latest acceptable arrival; extra-spend ceiling; number of travellers; baggage/mobility needs; preferred transport modes.
Search: flight offers/status where provider access is available; road routing/transfer times; weather context; curated train/bus schedule data or explicitly simulated alternatives.
Output: 2–3 feasible ranked options with total estimated extra cost, arrival estimate, transfer buffers, evidence/source timestamps, confidence/limitations, and recommended next action.
Approval: user must explicitly approve any booking, cancellation, payment, notification, or irreversible change.
Fallback: if live APIs fail or coverage is unavailable, switch to clearly labelled demo data and never describe it as live availability.
Out of scope for the first version
Universal access to every airline, train operator, bus operator, OTA or booking account.
Guaranteeing compensation, refunds, rebooking rights, or seat availability.
Autonomous purchasing or cancelling bookings without approval.
Claiming that weather alone proves a specific service was disrupted.
3. Example scenario: how the agent handles a disruption
Scenario for the demo (use seeded data, and label it as a simulation): a traveller’s flight is cancelled. They need to reach Bengaluru by 8:00 PM and can spend no more than ₹5,000 extra.
Stage
System behaviour
Detect/receive
The UI receives a cancellation event or the traveller selects “My flight was cancelled.” Save the event time and source.
Recover context
Load the traveller’s itinerary and booking metadata, if available; otherwise ask for flight number, current airport, destination, passenger count and deadline.
Clarify constraints
Ask only for missing decision-critical details: latest arrival, maximum extra spend, flexibility on bus/train/road, baggage, accessibility and willingness to use a nearby airport/station.
Plan
Deep Agent creates tasks: verify disruption, search flight alternatives, search ground transport, compute transfers, check weather risks, evaluate costs and rank.
Fetch evidence
Parallel read-only MCP tools call provider adapters. Each result includes source, fetched_at, currency, timezone, whether availability is confirmed, and demo/live status.
Validate
Deterministic engine removes options that exceed the budget, arrive after deadline, have impossible transfer times, or lack required accessibility.
Rank/explain
Rank feasible options by deadline fit, extra cost, arrival time, transfer risk and data confidence. Show why each option is included and what remains uncertain.
Approval
User selects an option. UI displays a review card: itinerary changes, total estimated cost, cancellation/refund caveats, provider link, and any action to be taken. Require explicit confirmation.
Execute/hand off
For MVP, open the provider’s official booking page or run a sandbox/simulated action. If a future booking API is integrated, revalidate price and availability before committing.
Verify and monitor
Store provider confirmation/reference only after provider success. Continue monitoring if supported; otherwise tell the user monitoring is not active.
4. Why this architecture
MCP is an integration layer, not the agent brain, data source, database, or safety policy. The Deep Agent decides which tasks to perform and invokes tools; the MCP server exposes narrow, typed operations; REST adapters communicate with providers; the deterministic engine checks hard constraints; the UI owns consent; and the database/audit log preserves the trip and decision trail.

MCP tools should return structured JSON content and include errors as typed, actionable results rather than raw stack traces.

10. Recovery scoring and constraint logic
Apply hard constraints before soft ranking. A high score must never rescue an option that misses a mandatory deadline or exceeds the user’s maximum budget.
Hard constraints
Arrival time must be at or before the traveller’s deadline, unless the user explicitly allows a late option to be shown as a fallback.
Estimated extra cost must be within the budget; if price is unknown, mark “price unverified” and do not silently treat it as zero.
Transfer arrival plus a configured safety buffer must be earlier than the next departure.
Passenger count, mobility/accessibility requirements, baggage constraints and allowed transport modes must be respected where data exists.
Any unverified or stale service is labelled uncertain and must not be described as confirmed.
Illustrative score
For feasible candidates only, normalize each component to 0–1 and compute:
score = 0.40 * deadline_fit + 0.25 * cost_value + 0.20 * transfer_safety + 0.10 * arrival_speed + 0.05 * evidence_confidence
Weights are initial design choices, not research-proven universal values. Tune them using test scenarios and user feedback. Always display the components and explanations so users can see why an option ranked first.
Illustrative pseudocode
def evaluate(option, constraints):    violations = []    if option.arrival_at > constraints.latest_arrival:        violations.append("ARRIVES_AFTER_DEADLINE")    if option.known_extra_cost is not None and option.known_extra_cost > constraints.max_extra_cost:        violations.append("OVER_BUDGET")    if option.has_impossible_transfer:        violations.append("TRANSFER_INFEASIBLE")    if constraints.required_accessibility and not option.accessibility_verified:        violations.append("ACCESSIBILITY_UNVERIFIED")    if violations:        return {"feasible": False, "violations": violations}    return {"feasible": True, "score": deterministic_score(option, constraints)}
11. API contracts and structured outputs
Normalize provider-specific data before returning it to the agent. Example candidate schema:
{  "option_id": "opt_demo_002",  "data_mode": "SIMULATED",  "source": "seeded_demo_provider",  "checked_at": "2026-10-21T09:30:00Z",  "currency": "INR",  "legs": [    {      "mode": "bus",      "origin": "Mangaluru",      "destination": "Bengaluru",      "departure_at": "2026-10-21T12:00:00+05:30",      "arrival_at": "2026-10-21T18:30:00+05:30",      "price": 1600,      "availability_status": "SIMULATED"    }  ],  "estimated_extra_cost": 1600,  "arrival_at": "2026-10-21T18:30:00+05:30",  "transfer_buffer_minutes": 0,  "feasible": true,  "score_components": {    "deadline_fit": 1.0,    "cost_value": 0.82,    "transfer_safety": 0.9,    "arrival_speed": 0.7,    "evidence_confidence": 0.3  },  "explanation": [    "Meets the 20:00 arrival deadline in the demo dataset",    "Within the extra-spend limit",    "Availability is simulated and must be checked with the operator"  ]}
Keep output schemas versioned. Reject malformed times, negative prices, missing currencies, duplicate leg IDs and impossible itineraries. Use UTC internally and preserve provider time zones.
12. Safety, privacy and trust controls
Human approval: no booking, cancellation, payment, or external message without an explicit approval action tied to a specific option, cost snapshot and expiry time.
Least privilege: read-only search tools by default; separate action tools; credentials scoped to minimum required permissions.
Provider verification: re-check availability and price immediately before any supported commit action; if changed, stop and ask again.
Idempotency: every external action uses a unique idempotency key to prevent duplicate bookings on retries.
Prompt injection defence: treat provider descriptions, emails and retrieved webpages as untrusted data, never as instructions to override policy.
Input validation: validate dates, currencies, IDs, traveller ownership and all tool arguments at the server boundary.
Secret handling: keep API keys in environment variables or a secret manager; never expose them to the model, browser bundle, logs or Git.
Audit trail: record tool name, actor, time, source, outcome and approval reference; redact unnecessary personal details.
Uncertainty: visibly distinguish LIVE, CACHED, STALE, SIMULATED and UNAVAILABLE data states.
Safe failure: on conflicting status or provider outage, stop committing actions, present alternatives with caveats, and provide official provider links.
MCP protocol security and authorization guidance evolves. Follow the current official specification and SDK guidance; tool annotations and descriptions are not a substitute for server-side enforcement [2][7].
13. Failure handling and resilience
Failure
Expected response
Flight API times out
Retry a limited number of times with backoff; use cache if freshness policy permits; otherwise mark unavailable and continue with other modes.
Weather API fails
Continue without weather input; show “weather check unavailable”; do not invent a forecast.
Provider returns stale data
Show timestamp and stale label; do not claim availability is confirmed.
No option satisfies hard constraints
Say no feasible option was found; ask whether deadline, budget or mode flexibility can change.
Conflicting disruption reports
Do not make an irreversible change; show conflict and request confirmation from operator/provider.
Agent output invalid JSON
Validate against schema; request structured retry once; then fall back to deterministic response.
MCP server disconnected
Circuit-break, surface tool unavailable, and use permitted fallback adapters or simulator.
Action result unknown
Do not retry blindly; query action status using idempotency/reference; tell user the state is unconfirmed.
Database unavailable
Fail closed for actions requiring approval persistence; do not execute irreversible action.

19. Risks and mitigations
Risk
Mitigation
No public live feed for a transport mode
Use authorized API/feed where available; otherwise seeded demo data with visible simulation label.
API quotas/costs or network failure
Caching, backoff, request budgets, timeouts and graceful fallback.
LLM hallucination about availability
Only render availability from typed provider result; require source timestamp and state.
Bad connection timing
Deterministic transfer buffer and conservative assumptions; mark unverified station transfers.
Unintended purchase/cancellation
Separate action service, approval snapshot, expiry, idempotency and audit.
Too much complexity for hackathon time
One MCP server, three provider adapters at most, one strong end-to-end scenario first.
Weak business assumptions
Interview travellers/agents and validate willingness to pay before quoting market size or revenue.
20. Business model and scaling
Initial users: travellers who need help during a disruption. Potential B2B customers include travel agencies, corporate travel desks, tour operators, and travel-insurance or mobility platforms. Potential monetisation options are a free basic consumer tier, premium monitoring, per-agent B2B SaaS, or an API integration fee. Treat these as hypotheses to validate, not proven market demand.
Stage 1: hackathon MVP with one regional corridor and simulated data.
Stage 2: real read-only flight and routing data, subject to access and terms.
Stage 3: authorized transport feeds, opt-in notifications, and trip monitoring.
Stage 4: B2B integration, role-based access, service-level monitoring, tenant isolation and analytics.
